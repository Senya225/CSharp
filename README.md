 MemoryLifecycle

Консольный проект на .NET для исследования сборки мусора и управления временем жизни объектов.

 Стек
- .NET 8.0 (или твоя версия)
- C 12
- Git, GitHub

 Цель и задачи
Цель: сформировать практические навыки анализа поведения сборщика мусора .NET, осознанного управления временем жизни объектов и оформления результатов исследования в виде воспроизводимого проекта GitHub.

Задачи:
1. Изучить поколения сборки мусора, большие кучи (LOH) и механизм DATAS.
2. Сравнить режимы Workstation GC и Server GC.
3. Реализовать классы с финализатором, интерфейсом IDisposable и конструкцией using.
4. Освоить полный паттерн Dispose и асинхронное освобождение через IAsyncDisposable.
5. Оформить результаты в виде проекта GitHub с осмысленной историей коммитов и README.

 Структура
- `src/MemoryLifecycle/Gc` — снимки счётчиков и сценарии нагрузки;
- `src/MemoryLifecycle/Resources` — классы, управляющие ресурсами;
- `src/MemoryLifecycle/Demos` — консольные сценарии;
- `docs` — отчеты по темам;
- `docs/images` — скриншоты результатов.

 Ответы на контрольные вопросы

 КТ №40. GC в .NET 10: поколения, регионы памяти (DATAS)

1. Почему новые объекты размещаются в Gen0? В чём суть гипотезы о смертности молодых объектов?
Новые объекты всегда размещаются в Gen0, потому что большинство из них живут очень недолго (временные строки, промежуточные результаты). Гипотеза о смертности молодых объектов гласит, что сборка Gen0 будет самой частой и быстрой, так как очищается небольшой участок памяти.

2. Как объект попадает в Gen1 и Gen2? Почему сборка Gen2 дороже сборки Gen0?
Если объект пережил сборку Gen0, он продвигается в Gen1. Если пережил и сборку Gen1 — в Gen2. Сборка Gen2 дороже, потому что сборщику приходится анализировать всю кучу (включая LOH), а не только молодое поколение.

3. Что такое LOH? При каком размере объект туда попадает и почему LOH по умолчанию не уплотняется?
LOH (Large Object Heap) — куча для объектов размером 85 000 байт и более. Она не уплотняется по умолчанию, потому что перемещение мегабайтных массивов обходится дороже, чем фрагментация памяти.

4. Что такое POH и какую проблему он решает?
POH (Pinned Object Heap) — отдельная область для объектов, которые должны оставаться по фиксированному адресу (например, при передаче в нативный код). До его появления такие объекты мешали уплотнению обычной кучи.

5. Что изменилось с переходом на регионы памяти в .NET 7 и новее? Почему регионы называют деталью реализации?
Каждый регион теперь принадлежит ровно одному поколению. Это позволяет точнее перераспределять память и уменьшает стоимость изменения границ поколений. Регионы не видны из кода C напрямую, поэтому их называют деталью реализации.

6. Что такое DATAS? Как он влияет на потребление памяти в контейнерах?
DATAS (Dynamic Adaptation To Application Sizes) — механизм, который поддерживает размер кучи пропорциональным объёму живых данных. При снижении нагрузки память возвращается операционной системе, что важно для контейнеров.

7. Что возвращают GC.CollectionCount, GC.GetTotalAllocatedBytes и GC.GetGCMemoryInfo? Почему HeapSizeBytes может быть равен нулю?
`CollectionCount` — число сборок поколения; `GetTotalAllocatedBytes` — суммарный объём запрошенной памяти (не уменьшается); `GetGCMemoryInfo` — снимок состояния кучи на момент последней завершившейся сборки. `HeapSizeBytes` может быть 0, если сборка ещё не выполнялась.

 КТ №41. Параллельная и фоновая сборка мусора

8. Сравните Workstation GC и Server GC по количеству куч, потокам сборки, целям и потреблению памяти.
Workstation GC использует одну кучу и один поток сборки, ориентирован на отзывчивость (клиентские приложения). Server GC создаёт отдельную кучу и поток для каждого логического ядра, ориентирован на пропускную способность (серверные приложения). Server GC требует больше памяти.

9. Что такое Background GC? Какие фазы сборки всё равно останавливают управляемые потоки?
Background GC — это режим выполнения сборки Gen2, при котором потоки приложения продолжают работу. Сборки Gen0 и Gen1, а также финальная фаза уплотнения Gen2 всё равно требуют кратковременной остановки (stop-the-world).

10. Почему GC.Collect(2, GCCollectionMode.Forced, blocking: true) не рекомендуется применять в производственном коде?
Он отбирает у сборщика возможность выбирать момент сборки с учётом реальной нагрузки, что может вызвать длительные и неожиданные паузы.

11. Как включить Server GC и как проверить, что режим действительно изменился?
Включить можно в `.csproj` через `<ServerGarbageCollection>true</ServerGarbageCollection>` или переменной окружения `DOTNET_gcServer=1`. Проверить можно через `GCSettings.IsServerGC`.

12. Почему Server GC может показывать больше сборок Gen0? Является ли это признаком деградации?
Нет, это не деградация. У Server GC несколько куч (по одной на ядро), и их бюджеты заполняются независимо, поэтому сборок может быть больше. Оценивать нужно по времени, аллокациям и паузам.

13. Почему одного короткого запуска недостаточно для сравнения режимов GC?
На результат влияют прогрев JIT, фоновые процессы и состояние машины. Нужно несколько запусков и усреднение.

 КТ №42. Финализируемые объекты. IDisposable. using

14. Когда вызывается финализатор? Почему его вызов считается недетерминированным?
Финализатор вызывает сборщик мусора, когда объект становится недостижимым. Момент вызова не определён — в консольном приложении он может вообще не выполниться до завершения процесса.

15. Почему финализируемые объекты живут дольше обычных?
Они попадают в очередь финализации, затем финализируются в отдельном потоке, и только после этого могут быть собраны. Из-за этого они переживают лишнее поколение.

16. Что гарантирует IDisposable.Dispose() и чем он отличается от финализатора?
`Dispose()` вызывается ровно тогда, когда решил разработчик (детерминированно). Это критично для файловых дескрипторов, сетевых соединений и других ресурсов.

17. Как компилятор разворачивает оператор using? Что происходит при исключении внутри блока?
В конструкцию `try/finally`, где в `finally` вызывается `Dispose()`. Это гарантирует освобождение даже при исключении.

18. Чем using-оператор отличается от using-декларации?
Оператор (`using (...) { }`) ограничивает область видимости блоком. Декларация (`using var ...;`) освобождает ресурс в конце метода или блока.

19. Что происходит при повторном вызове Dispose()? Как обеспечить идемпотентность?
Метод должен молча возвращаться (ничего не делать). Для этого используется флаг `disposed`.

 КТ №43. Паттерн Dispose. IAsyncDisposable (.NET 10)

20. Зачем нужен Dispose(bool disposing)? Какие ресурсы освобождаются при true, а какие при false?
Чтобы разделить освобождение управляемых (только при `true`) и нативных (всегда) ресурсов. Финализатор вызывает `Dispose(false)` и не трогает управляемые объекты.

21. Что делает GC.SuppressFinalize и почему его вызывают в Dispose() и DisposeAsync()?
Удаляет объект из очереди финализации. Если ресурсы уже освобождены вручную, повторный вызов финализатора не нужен.

22. Что такое IAsyncDisposable? В каких сценариях он необходим?
Интерфейс с методом `DisposeAsync()`, возвращающим `ValueTask`. Необходим для асинхронного освобождения ресурсов (закрытие сетевого соединения, сброс буфера на диск) без блокировки потока.

23. Почему рекомендуется реализовывать оба интерфейса — IDisposable и IAsyncDisposable?
Потребитель может знать только про `IDisposable` и не уметь использовать `await using`. Если реализовать только `IAsyncDisposable`, обычный `using` не скомпилируется.

24. Что делает await using? Чем он отличается от обычного using?
Вызывает `DisposeAsync()` и ожидает его завершения. Отличается от `using` тем, что не блокирует поток.

25. Как производный класс должен переопределять Dispose(bool) и DisposeAsyncCore()?
Переопределять с модификатором `override`, вызывать базовую реализацию и не дублировать публичные `Dispose()`/`DisposeAsync()`.

26. Как доказать, что финализатор не вызвался после Dispose()?
Вызвать `GC.Collect()` и `GC.WaitForPendingFinalizers()`. Если `GC.SuppressFinalize` сработал, сообщение финализатора не появится.

27. Какие ошибки типичны при реализации DisposeAsync()?
Отсутствие `try/finally` (нативный ресурс не закроется при исключении), забытый `GC.SuppressFinalize`, отсутствие проверки `disposed`.
